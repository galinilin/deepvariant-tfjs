# v3.2 — DV checkpoint shows hom_alt-only bias on near-any input

**TL;DR.** The released DeepVariant 1.8 WGS checkpoint we use
(`deepvariant.wgs.ckpt`) outputs `hom_alt ≈ 1.0` for virtually every
input that "looks like a real pileup," including hand-edited het
constructions on real golden tensors. Synthetic predictions in the v3.2
bottom canvas will therefore always show hom_alt, regardless of true
genotype. This is a model/checkpoint property, not a bug in our encoder
or sandbox.

## Investigation summary

After a clean encoder (`pileup-encoder.ts` validated 5/5 argmax against
upstream on real golden hom_alt samples), I observed v3.2 predicting
`hom_alt 1.0` on a 21/42 het scenario. I exhausted the obvious
suspects:

| Probe                                                     | Result      |
|-----------------------------------------------------------|-------------|
| Original synthetic het (24/45 alt support)                | hom_alt 1.0 |
| Synthetic with ~0.7% sequencing-error noise (50–60 ch5=254 cells) | hom_alt 1.0 |
| Coverage 800 reads → 42/79 alt support                    | hom_alt 1.0 |
| supports_variant ALL flipped to 152 (no support)          | hom_alt 1.0 |
| supports_variant ALL flipped to 254 (full support)        | hom_alt 1.0 |
| supports_variant ALL zeroed (empty)                       | het 0.998   |
| Row order shuffled                                        | hom_alt 1.0 |
| NO rows packed first, YES rows last                       | hom_alt 1.0 |
| Keep only top 10 read rows                                | hom_alt 1.0 |
| **Real golden hom_alt sample (sample 0, true class hom_alt)** | hom_alt 1.0 |
| **Hand-edit: flip ALL alt rows in real hom_alt → ref-supporters** | hom_alt 0.999 |
| Top 50 rows ch4 zeroed                                    | het 0.56    |
| All non-empty cells ch4 zeroed                            | het 0.998   |

Critical: **even editing a real golden hom_alt to look like het via
read_base + supports_variant + differs_from_ref edits keeps the model on
hom_alt 1.0**. The only operation that flips to het is *zeroing*
channel 4 (supports_variant) — i.e. removing the supports_variant signal
entirely, which doesn't correspond to a real het pileup.

I confirmed this on both:
- our TFJS uint8 model
- the float32 TFJS-converted model (`/root/dv-tfjs/out/tfjs_dv_wgs/`)
- **upstream Python Keras model loaded directly from
  `deepvariant.wgs.ckpt`** — same hom_alt 1.0 result.

So this isn't a quantization issue, a TFJS conversion issue, or an
encoder issue. It's a property of the released WGS checkpoint.

## Hypothesis

The released checkpoint may have been trained primarily (or evaluated
primarily) on hom_alt examples, and the het discrimination feature is
extremely fragile — only triggered by a very specific spatial pattern
of supports_variant that our synthetic doesn't reproduce. The
dv-tfjs README's ablation table (`run_real_pileups.py`) corroborates:
zeroing channel 5 collapses hom_alt → het (84 → 82 het), but zeroing in
half the rows is sufficient (84 → 69 het). The model treats *missing*
supports_variant differently than *present-but-non-supporting*
(value=152) supports_variant.

## Implications for v3.2

- The prediction display at the bottom canvas will read `hom_alt 1.0`
  for virtually any non-trivial scenario the synthetic sandbox produces.
- The encoder, candidate engine, and pipeline wiring are all correct —
  match/3.1 verified them on real BAM data.
- This is an intrinsic limitation of the released checkpoint vs our
  synthetic distribution. Cannot be fixed without re-training (out of
  scope for this repo).

## Mitigation in v3.2

Bottom canvas displays a banner labeling the prediction as "biased
toward hom_alt on synthetic inputs" so users aren't confused by what
they see. The prediction values are still useful as a diagnostic — they
demonstrate the model's actual response to encoded inputs, just don't
read them as ground-truth genotypes.

## Reproduction

`scripts/debug-encode.ts` runs the full probe set against the encoder
and model:

```
npx tsx scripts/debug-encode.ts          # synthetic het
npx tsx scripts/het-from-hom-alt.ts      # hand-edits real hom_alt → het
MODEL_FP32=1 npx tsx scripts/debug-encode.ts  # uses float32 model
```

Python upstream confirmation:

```
cd /root/dv-tfjs && uv run python -c "
import sys; sys.path.insert(0, 'vendor')
from dv_model import inceptionv3
import numpy as np, gzip, tensorflow as tf
m = inceptionv3((100,221,7))
m.load_weights('checkpoints/wgs/deepvariant.wgs.ckpt').expect_partial()
with gzip.open('/tmp/pileups.npy.gz','rb') as f: imgs = np.load(f).astype(np.float32)
print(m.predict(imgs[:1])[0])  # → hom_alt 1.0
"
```
